## What was checked

The installed extension was **0.6.24**. I visited 51 public pages in the user's Chrome profile and inspected Gmail in the same profile: **52 pages total**. The public-page sweep sampled DOM size, OLED-marked elements, visible `<img>` readiness, and computed contrast candidates. I visually inspected and exercised representative components on Amazon, Ralph Lauren, Walmart, Microsoft, eBay, and Gmail. These are snapshots, not full interaction or visual certification of every component on every site. Lazy images, CSS background images, and content outside the viewport are outside the image count. Contrast candidates are a triage heuristic and can be false positives.

The 52-page sweep found **zero failed viewport `<img>` elements at sampling time**. It did find confirmed failures in text/photo overlays and generated icon contrast. eBay's initially blank image slots populated after loading and were not a confirmed broken-image defect. Gmail's current search suggestion list was readable, though earlier installed versions had severe reader and suggestion defects.

## Amazon search and speed

On the user's Amazon search results page, OLED Night marked about 9,215 of 9,329 elements at the initial sample. A separate search tab later had about 10,801 marked of 10,940 after hydration. The sort is a browser-native `<select>`. With installed 0.6.24 active, four Chrome-control clicks took 2,584, 910, 1,234, and 794 ms; click plus accessibility observation took 4,354, 2,152, 2,450, and 1,899 ms. **These include browser-control overhead and are not input-to-paint measurements.**

After the user disabled OLED Night on that same Amazon tab, four additional measured clicks took 3,279, 1,479, 345, and 348 ms; click plus screenshot took 4,204, 1,893, 697, and 697 ms. The first two off clicks were also slow, so the delay cannot be attributed solely to the extension. Page hydration, browser-control overhead, and Amazon's own work remain plausible contributors. These runs are small and not randomized. The user has separately reported a much worse 5–10 second delay with the extension on; that experience remains a real unresolved performance target.

In a synthetic local page of roughly 3,000 nodes, a native-select pointer dispatch took 0.5–0.9 ms with the 0.6.24 source versus 0 ms after the candidate's select-event early return. This measures the extension handler and next animation frame, **not native popup latency**. A root class flip still costs tens to more than 100 ms in that fixture. Reverse-order repeat showed noise: baseline/candidate root-class medians were 42.1/30.2 ms on a dark page and 84.6/94 ms on a light page. Do not infer a general speedup from this microbenchmark.

## Candidate fix and remaining limits

The local candidate recognizes image/video siblings behind full-bleed text overlays, so it does not lighten originally dark text into near-white over a light photo. It also maps dark `::before`/`::after` foregrounds used as icons on recolored dark headers, and skips synchronous native-select interaction recoloring. Chrome fixture tests cover all three behaviors. This candidate is **not yet live-installed in the audited Chrome profile**, so the Walmart, Microsoft, and Ralph Lauren appearance is predicted by DOM evidence and fixture tests, not live verified.

The broad DOM sweep did not test all interactions or detect every icon, CSS image, lazy image, iframe, or personalized state. Sites with blocked/challenge/skeletal responses were excluded rather than counted as audited pages: Home Depot, Adidas, Figma, Kroger, AccuWeather, IMDb, WebMD, Pinterest, Dropbox, FedEx, Macy's, W3Schools, Spotify, Internet Archive, NYTimes, CNET, Britannica, and Yelp. Browser security interstitials were not bypassed.

## Later user feedback

The user supplied an Industrie Australia sale-page report captured with 0.6.24 showing dark mega-menu text and white icon/button blocks. An initial impression that 0.6.25 fixed these was incorrect: a later screenshot and a live Chrome inspection with 0.6.25 showed four white menu labels on white tiles and white square header icons. The expanded menu's existing `h3` labels had computed white text and white backgrounds, while OLED Night had only marked their foreground. The trigger had `aria-expanded=true` and `aria-controls=MegaMenu-Content-3`; the menu parent had `open=true`. The 0.6.26 candidate rechecks the controlled menu and observes `open`, with a regression fixture for the CSS-dependent sibling surface. The SVG icons use a `fill=none` symbol and `currentColor` stroke over an SVG root painted white; the candidate maps the tile without filling the outline. These are source and fixture validations, not live verification in the user's installed profile.

The user also reproduced a `missing captcha token` sign-in failure only with OLED Night on. The 0.6.25 report listed 1,609 styled elements and nine frames; hCaptcha frames were not directly styled. The Shopify password form loads a CAPTCHA bootstrap and provider on email focus. No credential submission or provider token was inspected. The 0.6.26 candidate leaves that entire protected authentication page native, including its form, scripts, and widget, and the regression fixture verifies zero OLED Night styling on such a page. This mitigates extension interference but does not prove which provider step lost the token.

## Sketchfab surface and container audit

The user's 0.6.25 screenshots show a white Getting Started card against a light-gray feed with OLED Night off, but no discernible card boundary with it on. The live Chrome tab confirmed `body` and `.newsfeed-getting-started` both computed as `rgb(0, 0, 0)` with OLED Night active; the card still had its original low-opacity black shadow, which is ineffective over black. The native card used a white background and soft shadow over a `rgb(242, 242, 242)` page. The report counted 1,710 styled elements and no shadow roots. This is a mapping collision, not a missing CSS border.

The active Useful Links panel computed as a dark teal gradient (`rgb(15, 92, 117)` to `rgb(12, 93, 121)`), nearly flattening its authored color variation, while its label computed `rgb(168, 168, 168)`. The generic mapping assigned all saturated gradient stops one lightness and demoted originally white text on colored surfaces. Version 0.6.27 varies the mapped gradient stops with source lightness and keeps white-on-color labels primary; it leaves flat controls at their previous dark level to protect contrast.

An inspected public model viewer used a canvas inside an iframe. The canvas was unmarked by OLED Night and had a transparent CSS background, but its embed document's body and root were forced black. Version 0.6.27 preserves a nested frame's transparent root when both original root surfaces are transparent and image-free, allowing a host backdrop to show through. This is verified on a transparent canvas fixture. The exact logged-out Sketchfab landing hero could not be directly toggled in the user's authenticated tab, so its final visual appearance still needs a live installed-version check.

The new container regression covers a raised white card, an explicit dark outline, a saturated gradient with white text, and a transparent canvas iframe that later becomes opaque. Chrome checks passed 174/174. The first outline implementation inspected both outline style and width on every element and failed the churn threshold twice (76 and 79 frames against 119 page-only). A width-only check passed the final suite at 113 frames against 122 page-only. The 0.6.26 baseline reached 102 against 121 in the same fixture; these short synthetic runs do not measure Amazon's native dropdown delay. This focused surface audit extends the earlier 52-page sweep; it does not imply those 52 pages were visually rechecked on 0.6.27.
